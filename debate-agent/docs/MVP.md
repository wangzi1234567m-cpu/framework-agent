# MVP：题解到框架稿

**状态：** 首版范围与验收草案。产品目标见 [产品需求](PRODUCT_REQUIREMENTS.md)，具体字段、技术和交付契约见 [架构设计](ARCHITECTURE.md)。MVP 的完成与“比通用模型更好”是**两项分别验证的结论**。

## 1. 首版用户旅程

```text
创建并保存辩题项目
  -> 题解 Agent：整理信息 -> 初稿 -> 自审 -> 至多一次定向修订
  -> 用户查看、编辑、确认当前题解
  -> 框架 Agent：读取确认题解 -> 论点规划/初稿 -> 自审 -> 至多一次修订
  -> 用户查看、编辑、保存工作区
  -> 用户明确确认 -> 生成不可变框架版本 -> 查看/导出
```

每次模型生成先是候选；Agent 自审不等于人工审批。框架任务在题解确认前拒绝；题解或工作区领先于任务快照时，迟到候选不得覆盖新状态。缺乏可核查事实时显式留下证据需求/不确定性。两个逻辑 Agent 可以使用同一个底层模型，但各自有独立写作方法和最终 DTO。

**本期不做：** 外网证据检索与溯源审核、已核验数据/案例保证、立论稿、自然语言局部编辑、完整的 RSI 循环、自动微调、复杂多用户权限体系和大规模并发优化。可展示用户提供的材料，但不得称未核验的材料为正式证据。新增样本进入 public 仓库前确认授权。

## 2. 可交付的最小模块

| 模块 | 完成条件 |
| --- | --- |
| 项目与身份 | 用户能创建、重新打开本人的项目；无身份时业务接口失败关闭，跨项目访问被拒。 |
| 题解闭环 | Agent 最终输出通过 `TopicResponse`；失败能诊断；修订插入新版本，批准仅针对当前版本，拒绝后不能生成框架。 |
| 框架闭环 | Agent 最终输出通过 `FrameworkResponse`；论点/机理/证据需求 `ref` 可映射；题解版本或工作区编辑冲突时拒绝覆盖。 |
| 编辑与确认 | 用户可保存结构化工作区；修改递增 `edit_version`；显式确认后创建不可变 CaseRevision，并可读取/导出该快照。 |
| 方法接入 | 两个 Skill 的已审版本可按 Job 固定加载；保存模型、Prompt、规则、Skill 版本/内容哈希；草案不能在生产启用。 |
| 最小评测 | 同条件批量生成、结构校验、匿名对照盲评和失败案例可复现；评价量表及独立测试题预先冻结。 |

API、ORM/迁移、Service、Skill 加载、Markdown 导出和任务 Runner 已能在合成 SQLite 测试中走完主流程；真实身份、已审核 Skill、真实 PostgreSQL 并发验证、前端与正式模型对照尚未完成。不能用合成通过替代真实用户与质量验收。

## 3. 质量对照：三组实验

| 组别 | 用途 | 控制条件 |
| --- | --- | --- |
| A：通用模型直接生成 | 回答产品是否优于日常通用模型使用 | 固定同一底层模型、题目、持方、材料、输出目标；记录提示词、调用数、时间、费用。 |
| B：相同步骤但不加载专有 Skill/规则 | 从流程增益中分离出写作方法的增量 | 与 C 保持相同的分析/起草/自审/修订预算和结构约束，只替换方法内容。 |
| C：完整题解确认 + Skill/Prompt 工作流 | 测产品表现 | 同题、同底层模型、同检索权限；题解人工确认和修改时间分别记录，不隐去额外人工投入。 |

A 与 C 比较整体产品价值；B 与 C 才能更直接检验 Skill/Prompt 是否有增量。若 A 是单次调用、C 是多次调用，必须同时报告成本/时间和资源差异，不把提升全归因于 Skill。B 的一般性结构提示与 C 的专有方法隔离；测试题及其优秀参考稿不得用于撰写/调试 Skill。

先冻结一批未参与经验提炼、题型和难度尽量分层的独立辩题（首轮建议至少 20 题，作为探索性结果而非统计显著性承诺）；若样本不足，明确标注“试点”而不作泛化宣称。每个题目记录材料授权与随机设置，匿名打乱 A/B/C 的产物，由至少两名辩手独立打分，分歧大时复核。保留原始评分、理由、评审一致性和全部失败题，而非只展示胜出例子。

## 4. 人机评分边界

**机器可核验：** 请求/响应 Schema、必填结构、`ref` 关系、批准题解版本的一致性、明显违背材料的引用、提供的来源能否定位、生成失败率、重试次数、成本、耗时和人工修改量。结构齐全**不等于**论证有说服力；未联网情况下机器不能证明任意现实数据为真。

**人评建议维度（各 1–5 分）：** 题解与判准 20%、论点分工 20%、机理连贯与深度 20%、事实谨慎性/证据需求 15%、攻防与比较 15%、实战可用性 10%。分值锚点：1=缺失或严重错误、3=基本可用但须明显修改、5=准确充分且可直接用于备赛；正式量表须为每个维度补齐独立的 1/3/5 行为例子。真实来源伪造、关键事实编造另计**严重错误率**，不被文笔得分抵消。评审模型可辅助标疑点，但先按人工结果校准，不能自行裁定胜负。

**决定规则在看结果前共同确认**：包括权重、盲评准入、并列/分歧处理、允许的成本增加、最低优势和严重错误上限。可将 C 相对 A 与 B 的逐题胜/平/负及人工修改时长作为主要指标；若小样本优势不稳定，应扩充测试而不是事后调阈值。尚未冻结量表和题集时，不宣称“已经超过通用模型”。

## 5. 端到端验收清单

- [ ] 空 PostgreSQL 能迁移，项目权限及读回路径通过集成测试。
- [ ] 两个 Agent 的分析、起草、自审、有限修订路径可执行；坏 DTO、超时和阻断缺陷有明确失败状态。
- [ ] 未确认题解不能启动框架任务；修改题解使旧批准失效，审批记录和旧正式版本仍可查。
- [ ] 任务重试幂等；模型返回晚于人工编辑时不覆盖；任务成功与候选保存同事务。
- [ ] 框架工作区可编辑、重新打开、确认并导出；CaseRevision 创建后不可改。
- [ ] 两个已审 Skill 包按固定版本加载，草案被拒；生成记录可定位方法和模型版本。
- [ ] A/B/C 盲测可复现，机器指标及两名人工评审结果可导出，重大事实错误单独报告。

未选定身份提供商、部署预算与实际规模前，不承诺具体吞吐/可用性数字；但数据隔离、失败恢复、版本保护和不泄露私有稿件是上线前必需条件。
